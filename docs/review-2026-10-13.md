# Beacon 扩展 review 与学习记录

本轮以公开 PHP API 可观察行为为入口，阅读了模块生命周期、Zend 参数/引用管理、共享内存、健康计算、负载均衡、治理 worker 与 governance.php。实现了有回归证据的第一轮修复；尚未完成生产并发安全验收。

## 本轮修复及证据

| 问题 | 原行为 | 修复与验收 |
|---|---|---|
| 非激活表读回退 | 新服务 store 后未 commit 已可读；清空提交后返回旧节点 | 只读 active；空表权威；public_snapshot |
| 批次快照缺失 | A/B 分批刷新可能让未更新服务回到旧版本 | 批次首次 store 复制已提交表；后续 store 共用 staged 表 |
| 部分节点字段残留 | 无效端口跳过后下一条可能继承 methods | 每条清零；必填字段、长度/NUL、状态、权重范围校验 |
| 整数/名称别名 | uint16 权重溢出，服务名截断/NUL 别名 | 拒绝非法服务名，跳过非法节点；保留合法状态整数兼容 |
| 零权重 | weighted 把 0 当作 1 | 零贡献，全零返回 null |
| 策略枚举 | setOpt 接受任意整数并静默 fallback | 仅允许 LB_* 枚举，非法值警告并 false |
| 回调跨请求 | 模块级 zval 保留到 MSHUTDOWN，下一请求执行旧回调 | 请求局部模块全局 + RINIT/RSHUTDOWN；三请求验收 |
| 回调自清除/替换 | 槽位清除可能释放执行中的 closure | 调用期间持有临时引用；先安装新引用再释放旧引用 |
| attach 失败泄漏 | 创建段后 shmat 失败未 IPC_RMID | 删除本次创建段，避免资源耗尽 |

原始 HEAD 在临时目录构建，相同的 snapshot/node validation/service names/weighted/options 五个 PHPT 全部失败；原始版本的多请求测试在后两次请求输出 `leaked0`，修复后均为 `-1`。当前完整套件 22 PASS / 0 SKIP / 0 FAIL；本机 PHP 8.5.11 NTS，未运行 Valgrind/ASan。

## 后续必须继续迭代的问题

1. **P1：共享内存并发快照协议。** `beacon_shm_store_nodes` 对非激活表复制/写入，但读者持有旧 active 指针后，写者再次 commit 并重用该表仍可覆盖它。`writing`、version、checksum 没有组成完整 acquire/release 重试或读者保留协议；当前 CRC 仅计算、不在读侧验证。应设计每表 generation + 有界快照复制/锁或 RCU 保留机制，并用多进程压力和故障注入验收；本轮取消未提交备份回退，没有实现损坏恢复。
2. **P1：治理 worker 所有权。** `beacon.c` MINIT 未检查 SAPI，普通启用 CLI 也会 spawn；RINIT 每百请求调用 ensure_running，各 FPM worker 可能同时重启。fork 后子进程 exec 在系统 extension_dir 寻找 beacon.so，未安装的构建目录并不保证可用。需要 master 专有协调、SAPI 条件和实际 fork/exec 成功握手，测试不能只用 kill(pid,0) 判断（僵尸也可能被视为存活）。
3. **P1：共享内存权限和 reload 生命周期。** key 默认只用服务名首字节，容易冲突；创建权限 0666 允许本机其他用户写入；header 仅检验 magic，没有验证 shm_version。旧 master 删除创建的段时，新 master 仍有映射，后来重启的 worker 可能连入另一段。应设计 pool 身份、权限、版本和所有权迁移，并做 reload 实测。
4. **P1：计数校准的长请求问题。** `beacon_shm_calibrate_busy` 超过 60 秒即清除仍活着的 worker；其后 RSHUTDOWN 无条件 unsigned 减 busy，可能下溢。槽位满时覆盖也可能造成计数不对称。需要生命周期 token、存活检查和可控时间的长请求/槽位满回归。
5. **P2：业务健康和注销契约未闭环。** reportHealth/deregister 只写 header 字段；当前 health_calculate/governance.php 没有消费 business_health_status/deregister_flag。文档描述的取最差状态、下一 tick 注销尚未实现，应补公共 API 到注册中心的集成测试。
6. **P2：ZTS 与请求选项隔离。** 本轮回调搬入模块全局，但扩展全局初始化、TLS 更新、其他静态状态和 setOpt 数值设置仍需 ZTS/多请求实测。没有把“支持模块全局”当作线程安全证明。

## 学习路线

先读 `php_beacon.h` 和 `beacon.c`，理解 MINIT 管模块资源，RINIT/RSHUTDOWN 管请求资源；再沿公开方法走 `beacon_api.c` → domain service → `beacon_shm.c`，最后读 fork/exec 与 governance.php。每次学习一条数据路径，都用一个小 PHPT 固定返回结构、输入边界和失败语义。

Zend 的核心是 zval 所有权：COPY 增加引用，COPY_VALUE 只搬移值；用户 closure 会持有请求对象，生命周期不能超过请求；析构函数和回调会重入，因此替换引用时要明确安装顺序。共享内存的核心是发布与复用的区别：atomic active 能发布表，但不能单独保证旧读者仍在读的表不会被重用。

对标 [Swoole](https://github.com/swoole/swoole-src) 的原生扩展测试入口和 [PHP 官方 PHPT 规范](https://wiki.php.net/doc/articles/writing-tests)，本轮采用独立场景、公开 API、精确 EXPECT、失败退出码；Yar/Redis 的模块/选项 API 风格仅作为代码组织参照，不据此宣称具备其成熟度。

下一轮建议先处理并发快照和治理单写者，再补 FPM reload、长请求和注册中心闭环；每轮通过 OpenSpec proposal/design/specs/tasks 留下决策和验收证据。

## CI 跟进修正

首次提交后的 [GitHub Actions run 38281542167](https://github.com/fangfengxiang/beacon/actions/runs/38281542167) 六个 PHP 版本的 Build/Test 均成功，但 E2E 在启动时因 GNU mktemp 不接受 `mktemp -t beacon-e2e` 失败。前一轮仅完成 PHPT 验收，没有在推送后核对整条流水线，这是验证缺口。

修复跨平台模板，同时隔离 make install/uninstall、显式配置 PHP CLI 的 pcntl/posix 依赖、给 exec 子进程传递可用的临时 INI 和 extension_dir，并以正常退出代替直接终止 sleep()。Linux PHP 8.2 容器独立构建通过全部 22 个 PHPT，真实治理 worker 的注册、保活、注销和安装卸载 E2E 也完整通过；macOS PHP 8.5.11 的 E2E 同样通过。FPM/reload/ZTS 范围不因这次 CLI E2E 而扩大。
